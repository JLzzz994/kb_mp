# kb_mp 鉴权与权限说明

## 1. 鉴权机制

### 1.1 JWT Token

- 算法：HS256
- 密钥：`JWT_SECRET`（.env 配置，生产环境建议 32+ 字节随机）
- 过期时间：默认 480 分钟（8 小时）
- Payload：`{sub: user_id, exp: ts, iat: ts}`

### 1.2 登录流程

```
1. POST /api/v1/auth/login {username, password}
   → 校验 bcrypt cost=12 密码哈希
   → 查询 users 表（status=1）
   → 加载 user_roles → roles → role_permissions → permission_codes
   → 写入 Redis bitmap: SET kb_mp:user_perm:{user_id} <bitfield> EX 300
   → 返回 JWT + 用户信息 + 权限码列表

2. 客户端持久化 token（建议 sessionStorage）
3. 后续请求带 Authorization: Bearer <token>
4. 后端从 token 解析 user_id → 查 Redis bitmap → 通过则注入 CurrentUser
5. Redis 命中失败 → 回退 MySQL 查询 → 自动写回 Redis
```

### 1.3 鉴权位图（Redis Bitmap）

- Key：`kb_mp:user_perm:{user_id}`
- Value：bitfield，bit 位 = 权限码索引（17 位覆盖全集）
- TTL：300 秒（5 分钟自动失效，下次请求重算）

为什么用 bitmap？
- 内存紧凑（17 权限码 = 3 字节）
- O(1) 查询
- 一次性 SET 整张位图，5 分钟不再查询 MySQL

### 1.4 权限码（17 个全量）

| 权限码 | 域 | 含义 |
|---|---|---|
| `user:read` | 用户 | 查询用户列表/详情 |
| `user:write` | 用户 | 增删改用户 + 重置密码 |
| `role:read` | 角色 | 查询角色 + 权限码 |
| `role:write` | 角色 | 角色权限分配 |
| `dept:read` | 部门 | 查询部门树 |
| `dept:write` | 部门 | 增删改部门 |
| `knowledge:read` | 知识 | 查询知识单元 |
| `knowledge:write` | 知识 | 增改 + 导入 |
| `knowledge:delete` | 知识 | 删除知识单元 |
| `knowledge:assign_permission` | 知识 | 配置四维权限 |
| `knowledge:check` | 知识 | 调用 check-permissions 接口 |
| `ai:chat` | AI | AI 问答 + 会话管理 |
| `dashboard:read` | 看板 | 数据看板所有端点 |
| `faq:read` | FAQ | 查询 FAQ |
| `faq:write` | FAQ | 增删改 FAQ |
| `faq:review` | FAQ | 审核（发布/驳回） |
| `gap:read` | 缺口 | 查询知识缺口 |

## 2. 知识四维权限

知识单元的访问控制由 `unit_permissions` 表配置（4 维 OR 逻辑）：

| target_type | target_id | 含义 |
|---|---|---|
| `global` | NULL | 全局可见 |
| `department` | 部门 ID | 该部门可见 |
| `role` | 角色 ID | 该角色可见 |
| `user` | 用户 ID | 该用户可见 |

### 2.1 鉴权流程（permission_filter 节点）

```
1. 召回所有候选 unit_ids（向量检索 Top-K）
2. 查询该用户对应的：department_id + role_codes + user_id
3. 加载所有候选 unit 的 unit_permissions
4. 鉴权 OR 逻辑：
   - 有 global 权限 → 通过
   - 有该 user_id 的 user 权限 → 通过
   - 有该 department_id 的 department 权限 → 通过
   - 有任一 role_code 对应 role_id 的 role 权限 → 通过
   - 否则未授权
5. 鉴权后通过 → 送 LLM；未授权 → SSE unauthorized 事件
```

### 2.2 配置示例

```json
// KU-003 研发中心技术规范：仅研发中心可见
{
  "permissions": [
    {"target_type": "department", "target_id": 1}
  ]
}

// KU-001 平台介绍：全局可见
{
  "permissions": [
    {"target_type": "global", "target_id": null}
  ]
}
```

## 3. 角色 → 权限映射

| 角色 | 权限数 | 权限码 |
|---|---|---|
| `system_admin` | 17 | 全集 |
| `knowledge_admin` | 11 | knowledge:* (5) + ai:chat + dashboard:read + faq:read + faq:write + faq:review + gap:read |
| `regular_user` | 4 | ai:chat + knowledge:read + faq:read + gap:read |

## 4. 中断（Interrupt）机制

AI 问答遇到以下情况触发 interrupt：

1. **召回为空**（faqs + units 都没命中）
2. **鉴权后为空**（召回命中但全部未授权）
3. **Top-1 评分 < 0.2**（命中度太低）

中断后：

```
SSE 流发出 event: interrupt
data: {"interrupt_id": "int-xxx", "reason": "no_recall", "message": "..."}

客户端弹出输入框 → 用户补充
POST /api/v1/ai/chat/resume {interrupt_id, additional_info}

后端 LangGraph 从 interrupt 节点继续执行
```

## 5. 安全建议

- [ ] 生产环境 JWT_SECRET 必须 32+ 字节随机
- [ ] bcrypt cost=12（演示）/ cost=14（生产）
- [ ] 定期轮换 JWT_SECRET（每 90 天）
- [ ] Redis 必须设置密码（演示期可省略）
- [ ] MySQL 账户最小权限（kb_user 仅 DML，无 DROP/GRANT）
- [ ] HTTPS 终止在 Nginx（演示期可省）
- [ ] 限流（演示期未启用，建议生产用 slowapi）
